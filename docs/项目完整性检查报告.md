## 二、数据库完整性检查

### 2.1 文件状态

| 文件 | 状态 | 说明 |
|------|------|------|
| schema.sql | ⚠️ 存根文件 | 仅含pgvector扩展，无表定义 |

### 2.2 表定义完整性

共31张表，分Phase 1-4定义：
- Phase 1基础表：sys_user、sys_role、sys_user_role、sys_permission、sys_role_permission、bid_project、bid_material、bid_document、bid_template、ai_task、sys_operation_log
- Phase 2知识库表：kb_knowledge_base、kb_chunk
- Phase 3资信标表：enterprise_profile、enterprise_certificate、enterprise_project_case、enterprise_team_member、material_library、material_usage_log、private_image_library、private_image_album、bid_qualification、bid_enterprise_info、bid_project_experience、bid_financial_data
- Phase 4工作流表：camunda_bpm_workflow_definition、camunda_bpm_workflow_instance、camunda_bpm_workflow_task、gateway_model_config、gateway_model_usage_log、gateway_model_switch_rule

**结论：表定义完整，覆盖所有Phase。**

### 2.3 索引完整性

- B-tree索引：70+个，包括唯一索引、联合索引
- 向量索引：2个（bid_document.embedding、kb_chunk.embedding，均为IVFFlat + cosine_ops）

**结论：索引覆盖主要查询字段，向量检索支持完整。**

### 2.4 数据库问题清单

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| 外键约束全缺失 | 🔴 高 | 所有外键关系依赖应用层保证，数据库层无约束，存在孤儿数据风险 |
| sys_user.dept_id无对应表 | 🔴 高 | sys_dept表不存在 |
| init.sql与init-db.sql内容完全相同 | 🟡 中 | 重复文件，需清理 |
| schema.sql为存根文件 | 🟡 中 | 应作为权威DDL文件，内容却为空 |
| material_library.tags使用VARCHAR但创建了GIN索引 | 🔴 高 | GIN索引仅对JSONB有效，VARCHAR+jsonb_path_ops索引为死代码 |
| gateway_model_config.api_key明文存储 | 🟡 中 | API密钥以VARCHAR(255)明文存储，无加密 |
| ON CONFLICT DO NOTHING无冲突目标 | 🟢 低 | sys_user_role等表INSERT的ON CONFLICT无unique约束匹配，无实际作用 |
| 端口号文档不一致 | 🟡 中 | 文档中ai-bid-document写为8084，但实际运行时端口存在歧义 |
